## 스마트컨트랙트 업그레이드 방식과 은행 시스템 변경 방식 비교 분석

## 레포트 내용

스마트 컨트랙트는 애초부터 코드의 불변성을 전제로 설계되었다. 그렇기에 한번 블록체인에 배포된다면 해커는 물론, 원작자조차 소스를 수정하거나 삭제할 수 없다.
이러한 불변성의 한계를 극복하고 어떻게든 업그레이드를 하기위해 등장한 방식이 바로 Proxy 패턴과 delegateCall 기능이다. 은행의 시스템을 포함한 대부분의 시스템이 서버로직과 DB로 나누어져 있듯이 Proxy 패턴 또한 데이터를 보관하는 Proxy와 실제 계산을 수행하는 로직 부분이 두개의 컨트랙트로 쪼개어져 배포된다. 이러한 방법을 통해 데이터는 Proxy에 영구히 보관하여 불변성을 유지하고, 새로운 로직 컨트랙트는 Proxy가 바라보는 방향만 바꿔주어 관리할 수 있다.
delegateCall 기반의 업그레이드 방식은 위의 언급된 로직부분 변경하고, 그 새로운 로직을 delegateCall로 불러주는 것이다. 그럼 은행시스템과 같이 DB는 그대로 존재하고, 서버로직만 업그레이드 되는 형태와 유사하게 작동한다.
다만, 은행시스템의 배포/변경 방식과 차이는 프로그램을 직접적으로 변경하는지에 따라 다른데, 이부분은 스마트컨트랙트에서도 유사하게 구축할 수 있다. 
예를들어 현재 은행시스템에서는 프로그램을 직접 수정하여 해당 프로그램의 버전이 올라가고 배포시점에 새로운 버전의 프로그램을 바라보고 로직이 수행되는데, 위의 언급된 Proxy 패턴은 이전 버전의 로직은 버려지고 새로운 로직을 생성하고 그쪽으로 라우팅하는 방식이기 때문이다.
다만, 스마트컨트랙트에서도 신규되는 로직을 버전관리하면 기존 형상관리와 비슷한 형상을 띌 수 있을 것으로 예상된다.
스마트컨트랙트 업그레이드 방식에서 발생할 수 있는 위험요인은 스토리지 충돌이다. delegateCall은 변수의 이름이 아니라 선언된 순서를 기준으로 데이터를 덮어쓰는데, 버전을 올리면서 실수로 순서를 바꾸어버린다면 데이터가 덮어씌워지며 자산에 대한 데이터 정합성이 깨지거나, 운영통제권을 잃을 수 있다.
물론 위의 오류는 은행시스템에서도 충분히 발생할 수 있다. 다만, 이를 막기위한 여러가지 통제장치를 마련해놨다. 우리가 배포할때마다 겪듯이, 현업인수테스트-동료코드리뷰-프로젝트PM결재-관리자-QA 등 휴먼에러를 막기위한 일련의 프로세스를 진행하고 있다. 추가적으로 혹시라도 문제가 발생하더라도, 소스를 즉각 롤백하고 데이터 또한 복구할 수 있는 방법을 구비해두었다.
운영/통제 관점에서 가장 큰 차이는 복구 패러다임의 차이다. 은행의 통제 핵심은 문제가 생기면 '과거'로 되돌린다는 것이다. 최근 형상관리시스템 개발자 점검표에 추가된 것처럼, 롤백이 가능한지, 데이터도 복구할 수 있는지에 대해 묻듯이 원복을 시도하고자 한다.
반대로 스마트컨트랙트는 과거가 아닌 '전진 조치'이다. 위의 언급된 스토리지 충돌이 발생하여 데이터가 망가지더라도 롤백할 수 없으며, 유일한 해결책은 버그를 수정한 다음 버전을 다시 배포하여 데이터도 수정하고 프로그램도 해결해야한다.
또한 통제는 Week 6의 과제에서도 언급되었는데, 은행은 내부망 방화벽 안에서 코드 자체에 대한 접근통제를 하는 반면, 스마트컨트랙트는 누구나 코드를 볼 수 있기 때문에 Proxy가 바라보는 것을 변경하는 권한을 통제한다.

## 핵심 질문 (참고용)

아래 질문을 참고하여 작성하면 도움이 됩니다.

- 스마트컨트랙트는 왜 “업그레이드가 어려운 구조”인가  
- delegateCall 기반 업그레이드 방식은 어떤 원리로 동작하는가  
- Proxy 패턴(로직/데이터 분리)은 어떤 문제를 해결하기 위해 등장했는가  
- 은행 시스템에서의 배포/변경 방식과 무엇이 다른가  
- 스마트컨트랙트 업그레이드 방식에서 발생할 수 있는 위험은 무엇인가  
- 은행 시스템에서는 변경 시 어떤 통제(승인, 검증, 롤백 등)를 수행하는가  
- 두 구조를 비교했을 때 운영·통제 관점에서 가장 큰 차이는 무엇인가
